## 1. Scope, and how Olcay works

contracts, a Figma importer plugin, Storybook docs. The work is the MAP-474 change list: each row
built on all three platforms, reviewed adversarially, verified, merged. Vue waits (decision 2). The

**How Olcay works** (standing instructions):

- "Ask questions if you need my answers; apart from that, do instead of waiting for me — obviously
  if not breaking anything." Merging my own green, verified PRs is authorised. Olcay answers through
  the question tool, with a recommended option first.
- "No hacks, no cheats — do it properly." An adversarial self-audit before "done"; measured
  evidence, not claims. "We don't have to do everything here" (decision 21): what the platform
  already gives, Kozmos doesn't build.
- **Never**: handle a token or key (Figma reads go through `scripts/figma-rest/with-figma-token.sh`);
  delete a secret, a branch, a PR or a project directory (say so and leave it to Olcay); `git add -A`
  or a directory; a bare `git stash`; Rebuild in the Figma plugin (Update only); "Import Foundations";
  publish to npm (Olcay dispatches the release).
- Examples are built from Kozmos parts only; gaps are reported, not worked around.

**How I verify** (every PR):

- New tests are written first and fail **on an assertion** against the unfixed code; I read the
  output. A control that could not fail proves nothing (mutate the code and watch the test fail).
- `ci-local --job web` is only CI's "Web Build & Test"; the browser shards, the bundle budget and
  Visual Review run on GitHub — run the ones you touch yourself, each on its own port (CI's pattern:
  `python3 -m http.server <port> --directory apps/docs/storybook-static` and
  `STORYBOOK_URL=http://127.0.0.1:<port>`). Only one session at a time may run `ci-local --job web`.
- Native: prove the new tests ran **by name** — `xcrun xcresulttool get test-results tests --path
  <dir>/TestResults.xcresult`, Android's `build/test-results/testDebugUnitTest/TEST-*.xml`. GitHub now
  builds iOS on a PR that touches it (decision 24), but the simulator render tests still need the
  local run.
- Background agents work in their own worktrees on their own ports and open PRs without merging; I
  review each diff, re-check its evidence and merge.

## 7. How merging works now

- **19 required checks** on `main`, all GitHub Actions (app 15368): CI's `Web Build & Test`,
  `Core Pipeline & POI Gallery`, `Android Build`, `iOS Build` and twelve browser shards,
  `analyze-bundle`, `lighthouse`, `Visual Review`. Matched **by name**: renaming a job or shard
  means updating the list in the same change, and a new always-running check must be added to it.
- **The merge queue** (repository ruleset "main: merge queue"): merge commits, all-green grouping;
  auto-merge (`gh pr merge <n> --auto`, the app's auto-merge, or "Merge when ready") joins the
  queue; the queue runs the required checks on the PR combined with the latest `main` and merges
  only if they pass. Repository admins can bypass it for an emergency.
- **iOS Build** (decision 24): a `Changes` job decides; skipped when a PR doesn't touch iOS inputs,
  which passes the check deliberately.
- **Changesets**: a PR that changes what `@kozmos-ds/react`, `icons`, `product-contracts` or
  `tokens` ships needs a changeset naming it (`changeset-required.mjs`); an empty changeset waives
  it. Dependabot bumps of a published package's runtime `dependencies` need one pushed to their
  branch.
- **Visual Review**: a PR that changes how a story looks records its baselines (Actions → Visual
  Regression → Run workflow on the branch with `record`, check the bot commit, then push again —
  a workflow's commit starts no checks). Never record on a bare Mac.
- **The first queued merge must show**: `iOS Build` skipped and green on a docs-only PR, the
  checks re-run on the merge group, and the PR merged by the queue.

Undo, if ever needed: the ruleset is deleted by Olcay in Settings → Rules; the required list is a
PATCH to `…/branches/main/protection/required_status_checks` (night handoff decision 13 has the
original).

## 8. Releasing

1. **A version PR**, "release: version X and approve it": `pnpm version-packages` consumes every
   changeset (the private apps are bumped too); write `release/plan.json`
   (`{schemaVersion: 1, tag, packages: [{name, version}]}` for the public packages that changed);
   `pnpm skills:build` (the AI changelog and inventory carry the versions, and `skills:check` fails
   without it). Prove it: `readPlan()` from `scripts/release/verify-request.mjs`, `pnpm test:release`,
   `pnpm pack` react and read its sibling pins, `pnpm packages:install:check`.
2. **Olcay merges it and dispatches `release.yml` at once** (§3.1 has the inputs and why).
3. **React pins its siblings exactly** (`workspace:*` → exact at publish): a react that needs a new
   icon or contract field needs those packages released with it.
4. Measure API changes against the published tarball (`npm pack <pkg>@<version>` and diff its
   `index.d.ts` with a fresh build), never from memory: the diff corrected this session's own notes.
