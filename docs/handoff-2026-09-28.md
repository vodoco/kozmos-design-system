## 7. How merging works now

- **19 required checks** on `main`, all GitHub Actions (app 15368): CI's `Web Build & Test`,
  `Core Pipeline & POI Gallery`, `Android Build`, `iOS Build` and twelve browser shards,
  `analyze-bundle`, `lighthouse`, `Visual Review`. Matched **by name**: renaming a job or shard
  means updating the list in the same change, and a new always-running check must be added to it.
- **Up to date to merge** (decision 25): when `main` moves, a PR shows "behind" and cannot merge until
  it is updated — `gh pr update-branch <n>` or "Update branch" — and its checks run again; auto-merge
  then merges it once they pass. Merging several PRs is therefore one at a time: merge, update the
  next, wait for its checks. (A merge queue would automate that; it needs the repository to move to an
  organisation.)
- **iOS Build** (decision 24): a `Changes` job decides; skipped when a PR doesn't touch iOS inputs,
  which passes the check deliberately.
- **Changesets**: a PR that changes what `@kozmos-ds/react`, `icons`, `product-contracts` or
  `tokens` ships needs a changeset naming it (`changeset-required.mjs`); an empty changeset waives
  it. Dependabot bumps of a published package's runtime `dependencies` need one pushed to their
  branch.
- **Visual Review**: a PR that changes how a story looks records its baselines (Actions → Visual
  Regression → Run workflow on the branch with `record`, check the bot commit, then push again —
  a workflow's commit starts no checks). Never record on a bare Mac.
- **Visual review on your Mac** (`scripts/visual/docker.sh`): the image's **amd64** build, as CI, even
  on Apple silicon — recording is byte-identical to CI's; a full compare takes about 5 minutes under
  emulation. `VISUAL_PLATFORM=linux/arm64 pnpm test:visual` compares natively in about 1 minute (equal
  within tolerance only); never record that way. `pnpm test:visual:update --grep <story>` now passes
  its arguments to Playwright.

Undo, if ever needed: `strict` and the required list are one PATCH to
`…/branches/main/protection/required_status_checks` (night handoff decision 13 has the original).

## 8. Releasing

[docs/release-process.md](release-process.md) is the procedure. In short:

1. **A version PR**, "release: version X and approve it": `pnpm version-packages` consumes every
   changeset (private packages are not versioned, decision 28); write `release/plan.json`
   (`{schemaVersion: 1, tag, packages: [{name, version}]}` for the public packages that changed);
   `pnpm skills:build` (the AI changelog and inventory carry the versions, and `skills:check` fails
   without it). Prove it: `pnpm test:release`, `pnpm pack` react and read its sibling pins,
   `pnpm packages:install:check`.
2. **Merge it** (19 checks, up to date) and wait for `main`'s push CI run on the merge. Merge nothing
   else until the release is out: the release job refuses a candidate that is no longer `main` HEAD.
3. **`pnpm release:preflight <sha> <ci-run-id>`**: the credential check, the release job's own
   request, evidence and plan checks against the live run, and a refusal if npm already has any
   planned version. It prints the dispatch command.
4. **Olcay dispatches it** (or asks me to) **and approves `npm-release`** under "Review deployments".
   Never me.
5. **From the registry**: each version, its `latest` tag and react's exact sibling pins, and a clean
   install that renders; then **`pnpm release:tag <sha>`** (`--dry-run` first).
6. **React pins its siblings exactly** (`workspace:*` → exact at publish): a react that needs a new
   icon or contract field needs those packages released with it.
7. Measure API changes against the published tarball (`npm pack <pkg>@<version>` and diff its
   `index.d.ts` with a fresh build), never from memory: the diff corrected this session's own notes.
8. **The next release is provenance's first.** If npm refuses the attestation (a `repository` that
   doesn't match, or no OIDC token), the first package fails before anything is published: fix,
   merge, and run steps 2–5 again.
