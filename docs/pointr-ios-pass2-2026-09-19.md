## What the card shows now

`SDKPOIAdapter.details` maps a place into `KozmosPOIDetailsPresentation` on plain values, so every
rule has a test that needs no SDK object.

- **Taxonomy attributes** go through `TaxonomyPresenter`, a rule-for-rule port of the web's
  `POITaxonomy.fixtures.ts` over the same pinned 10.12.0 projection (`TaxonomyProjection.swift`,
  generated by `scripts/sync-ios-taxonomy.mjs`; CI checks it is fresh). Labels and value labels
  from the dictionary; value icons for enum and array values, the property icon for booleans and
  integers; `order` for chips, `highlight` for the summary row; `false` only when the dictionary
  names it; zero as a value; the crowd level carrying the wait; the product's highlight-only set;
  dictionary colours onto the card's tones and nothing invented; three highlights after sorting.
  The SDK's typed fields replace their raw twins in the attributes. The web's twelve edge cases
  pass natively.
- **Rating and price** come from the SDK's numbers, where the taxonomy only says "object": absent
  on the sentinel, off the scale, or on a scale other than the card's four (reported).
- **Contacts.** A button becomes an action only with an address the host can open — a web address
  with a scheme and a host, a phone number with digits, a mailbox with a host — and only the host
  opens it. A simulator cannot call, and the card is told ("Calling isn't available on this
  device.") rather than nothing happening. Unopenable or custom buttons are diagnostics.
- **Opening hours** are the venue's text, plain over escaped HTML, never an open-or-closed claim;
  the disclosure's note says so. A structured schedule with slots would be reported, not rendered:
  PointrKit 10.3.0's reference says only "Keys are days of the week" and never which day comes
  first, and Design-QA has no slots to measure it from.
- **Description** as plain text, dropped when it is only the name again. **Tags** as before.
- **Diagnostics** go to the unified log, subsystem `com.kozmos.pointrqa`, category `poi`, one line
  per issue, place content only.

Availability stays `nil` — no status is inferred — and route estimates wait for Pass 3.

## Upstream findings, for §9's list

1. **Hours live in CMS text, not the taxonomy object.** Every structured schedule is empty; the
   venue types hours into `hours of operation text` and an HTML twin. The adapter reads those two
   keys — venue-specific, named in one constant.
2. **PointrKit flattens the day names away.** `openingHours` is `[PTRPoiDaySchedule]` with no day
   field; the reference documents no order. Until Pointr documents it, structured hours cannot be
   rendered honestly.
3. **`Payment Options` is prose, not `paymentMethods`.** "Cash or credit card (Mastercard, Visa…)
   are accepted" as escaped HTML. It is not mapped; the taxonomy value list would give icons.
4. **`unitNumber` is not `unitId`**, and the category strings (`Apple Primary Category`, `Google
Places Type`) are not the taxonomy's `mainType/subType`. The card shows no category label yet:
   a display name for a type needs a projection of the taxonomy's types, which the web examples do
   not carry either.
5. **Keywords are search terms**, not display tags, and the dictionary agrees (segment "Search",
   no order). They belong to item F.
6. **A description that repeats the name** ("Alamo ", "Avis") is content, dropped on the card.

## Not done

Category labels (item 4 above). Keywords in search (F). Routing and route estimates (Pass 3).
The web product's own button mapping — the web examples take supplementary actions from fixtures;
a web host on live PointrKit data needs this adapter's rules too. Android: none of this.
