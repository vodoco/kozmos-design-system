# Input

Inputs allow users to enter text into a UI. They typically appear in forms and dialogs.

## Usage

Use inputs to get text data from the user. Common use cases include:
- Forms (Name, Email, Password)
- Search fields
- Filtering data

## Actions

`action` puts a button inside the field's end (GAP-154), drawn as PasswordInput's reveal is: as tall
as the field, inside its border, with its own focus ring, and the field's text kept clear of it.
Hovered, it draws a fill inside itself, 4 px in from its edges (36 across in touch, 32 in compact),
its corners the field's less 4, so the field's edge stays drawn round it (decision 164); it draws
none at rest, disabled or in forced colours. It is disabled with the field.

- `{ kind: "copy" }` copies the field's value: for a value a product shows and never edits, a
  feature's ID, with `readOnly`. Once copied, a polite live region says "Copied" (`copiedLabel`),
  and a check stands in for the copy icon for two seconds; copied again, it says so again. If the
  browser refuses the clipboard, it says nothing. The button is named "Copy" (`label`); `onCopy`
  receives the value.
- `{ kind: "toggle" }` is a pressed button with its own name: the Featured star at a field's end.
  `label`, `icon`, `pressed` and `onPressedChange` are the product's. Pressed, it is drawn as a
  pressed ToggleButton is, as the MAP-64 design draws its Featured star: the theme fill under the
  icon, in the fill's foreground, in the hover fill's shape (decision 165), so the state is a shape
  and not a colour alone (WCAG 1.4.1), whatever the icon. Hovered, the fill is the themed Button's
  hover; in forced colours it is Highlight, hovered or not.

Giving a field an action, or taking it away, keeps the same input, its focus and a value typed
into it.

## A mixed value

With several features selected, a property whose values differ is one field for all of them
(GAP-153, decision 132). `mixed` says the field stands for those values: it shows none of its own,
"Multiple values" (`mixedLabel`) in its place as the placeholder, and is described with it, so a
screen reader says it with the field; SwiftUI gives VoiceOver the words as the field's value, Compose
gives TalkBack them as its state. Input, NumberInput, Select and Combobox take it, with the same
names on every platform.

It is controlled, as the selection is the product's. The visitor's first edit comes through the
field's own change callback, and the product clears `mixed`, so the field keeps its mixed state
until it is edited. Give `onResetMixed` for a field whose values differ: once the field is no longer
mixed it draws "Reset to multiple values" (`resetMixedLabel`) under the field, a text button at its
start, never while it is disabled or read-only. Pressed, focus goes back to the field, and the
product drops the edit and sets `mixed` again. A multi-selection's editor holds one edit per field
and derives both from it, so a new selection needs nothing reset:

<Canvas of={InputStories.MixedValue} />

```tsx
const differs = values.some((value) => value !== values[0]);
<Input
  label="Name"
  mixed={differs && edit === undefined}
  value={edit ?? (differs ? "" : values[0])}
  onChange={(event) => setEdit(event.target.value)}
  onResetMixed={differs ? () => setEdit(undefined) : undefined}
/>;
```

An uncontrolled field drops its default value while mixed, and its typed text is emptied on reset.

```kotlin
import androidx.compose.runtime.Composable
import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.remember
import androidx.compose.runtime.setValue
import com.kozmos.components.input.KozmosInput

@Composable
fun NameAcrossSelection(names: List<String>) {
    val differs = names.distinct().size > 1
    var edit by remember(names) { mutableStateOf<String?>(null) }
    KozmosInput(
        value = edit ?: if (differs) "" else names.first(),
        onValueChange = { edit = it },
        label = "Name",
        mixed = differs && edit == null,
        onResetMixed = if (differs) ({ edit = null }) else null
    )
}
```

```swift
import SwiftUI
import Kozmos

struct NameAcrossSelection: View {
    let names: [String]
    @State private var edit: String?

    var body: some View {
        let differs = Set(names).count > 1
        KozmosInput(
            text: Binding(get: { edit ?? (differs ? "" : names[0]) }, set: { edit = $0 }),
            label: "Name",
            mixed: differs && edit == nil,
            onResetMixed: differs ? { edit = nil } : nil
        )
    }
}
```

## In Safari

`className` lands on the field. A utility class passed there styles it in Chrome, Edge,
Firefox and Safari 26.4, and is ignored in Safari 26.0 to 26.3, where the field keeps its
own look: those versions apply no `@scope` rule to an `<input>` (GAP-174), and Kozmos's
utilities are scoped. Use the props, the provider's `tokens`, an inline `style` or your
own CSS, and `wrapperClassName` for the layout around it. Guides › Platform support ›
Fields in Safari has the detail.
