# AdaptiveMapShell

Map-engine-neutral layout driven by its **container**, not the browser viewport.
Give the shell a definite height (or a bounded parent for its default `height: 100%`).
The old 448px minimum has been removed so a short landscape host can constrain it.

Auto presentation uses a side panel in a local region at least 720×160px, otherwise
a bottom panel. Override with `panelPresentation`; a bottom sheet rests at one of its `panelDetents` — collapsed (a fifth of the shell, or
the content's peek anchor, marked with `panelPeekAnchorProps`), medium (54 %) and large
(94 %) by default, resting at medium — dragged anywhere on it and snapping to the nearest;
its content scrolls only at the largest detent. `panelFraction` and `panelSizing="content"`
are single-detent shorthands. Read the resolved
panel bounds from `onLayoutChange`. `panelPlacement` is logical and follows inherited RTL direction.

`panelHeader` sits under the sheet's grip and above the panel's content, and does not
scroll with it, so a search field or a chosen category stays put while the results under
it scroll. Every detent counts it: a sheet fitted to its content includes it, and a
collapsed sheet is always tall enough to show all of it (a header that fits leaves the
collapsed detent where it was; a taller one raises it). A peek anchor, in the header or the
content, still decides where a collapsed sheet rests. A vertical drag on it always
moves the sheet, however far the content has scrolled; a sideways one stays with the
header, for a row of chips that scrolls. Under a grab handle it keeps its first control
clear of the handle's target (WCAG 2.5.8). In a side panel it is the panel's first row.

## Accessible control regions

The `controls` slot has a named landmark, `controlsLabel` (default **Map controls**).
Both registered bottom corners share a second landmark, `bottomControlsLabel`
(default **Map corner controls**). Pass non-empty translated names; keep the two
names distinct when both regions are present. These labels describe groups of map
controls, not the map renderer or the details panel.

SwiftUI exposes named accessibility containers with the same labels; Compose exposes
named traversal groups. Child controls keep their own names, states and actions—these
containers do not merge the buttons into one control or add toolbar arrow-key behavior.
Omitted slots create no control region. Regions hidden because they cannot fit are
also hidden from accessibility, while their state remains mounted.

The built-in FloorSelector's trigger stays in the bottom landmark; its portaled popup
is a separately named dialog connected through `aria-controls`, with its tooltip
descriptions inside that dialog. Custom popup content must preserve its accessible
ownership and visibility lifecycle; the shell cannot reparent arbitrary consumer portals.

## Registered bottom corners

Use `controlsBottomStart` for the logical start corner and `controlsBottomEnd` for
the opposite corner. Place controls directly in these slots, not inside a second
`MapOverlay`. The shell measures them together, clears its top bar, legacy controls
and panel, and mirrors their placement in RTL. If the two corners cannot share a
row, start stacks above end without shrinking their controls. Give slot content a
width that can fit the host. The shell does not make oversized child content responsive.

If the remaining height cannot fit the complete region, it stays mounted but is
hidden and non-interactive until space returns. Empty space between the controls
continues to accept map gestures. Expanded popup containment is a separate concern:
these slots are not a replacement for a bounded popup implementation.
In particular, a portaled popup has its own visibility and focus lifecycle; hiding
its anchor region is not proof that the popup has closed. Host integration must
coordinate that transition. FloorSelector already coordinates it through the registered
shell region: its popup is bounded, scrolls to selection and dismisses when the region
disappears. Beside a long same-side panel, it may move horizontally into the clear map
region. This behavior does not automatically extend to arbitrary custom popup children.

`bottomControlsPadCamera` defaults to `false`. Enable it to reserve a conservative
bottom camera band. React always includes the visible region's bounding envelope in
`onLayoutChange().occlusions`; that envelope includes the space between corners.
Native implementations report edge insets, not React's full rectangle snapshot.
Caller insets are inputs—do not feed the resolved callback back into those inputs.

SwiftUI and Compose expose the same slot names and opt-in flag. Native shells also
respect a host shorter than 448pt/dp; give them a bounded parent. Existing `controls`
remains supported. Independent `MapOverlay` siblings do not gain collision avoidance
automatically: register opposite corners with the shell.

The panel tells its content how much space it already leaves above it, so a part that brings its
own top padding can top it up rather than add to it:

- `--kozmos-panel-inset-top` is the space already supplied above the content: the grip's
  16px row, the 16px gap below a `panelHeader`, or the `1rem` top inset in a gripless
  sheet or side panel. Do not add another 16px spacer below `panelHeader`.
- `--kozmos-panel-clearance-top` is how far the content's first control must still sit below that
  so the grip's 16px target keeps its WCAG 2.5.8 spacing: 4px under a grip, `0px` elsewhere. A
  panel header keeps the same clearance itself.
- The content box is no size container, so a product's own container queries in content it hosts,
  unnamed ones and `cqi` or `cqw` units among them, read the product's own containers. Only the
  details card below is a container, of itself.

Migration: remove redundant top padding on an outer content wrapper where the shell now
supplies the first 16. For example, a gripless navigation panel's `p-4` wrapper becomes
`px-4 pb-4`; its RouteSummary retains padding inside its own card. The same ownership rule
applies to native outer stacks/columns. Keep intentional card-internal padding and spacing
between content rows; only the duplicated shell-edge or fixed-header gap is removed.

Every part at the top of the panel keeps the grip's clearance, so no first control sits inside the
grip's 24px circle:

- `BrowseCategoriesPanel`, whose first row is its search row (or its tiles when it has none), and
  `RoutePreviewPanel`, whose first row is its destination, top their 16px up to what the panel
  leaves, `max(clearance, 16px − inset)`. The search field and the destination sit as far from the
  panel's top as from their side, and 4px further under a grip (GAP-083 and decision 14; they sat
  33px down and 17px in).
- `POIResultList` brings no top padding of its own, so it keeps only the clearance. Under a grip
  its first result used to sit inside the grip's circle.
- `POIDetailPanel` in its `sheet` presentation, which paints no surface of its own, tops its
  header's 16px up to the inset and drops the clearance wherever its header's buttons stay clear of
  the grip's circle anyway: its close button sits 17px from the top and 17px from the side. Where
  they would not, on a narrow panel (under 340px wide with favourite, save and close), it keeps the
  clearance too, 21px and 17px (decision 51, refining decision 14 for this header). Hosted here,
  the card is an inline-size container of its own and fills the content box, and its header reads
  the card's width.

The two values describe the panel's top. A part you place under a row of your own is not at the
top: put that row in `panelHeader`, which keeps the grip clear itself, or set both properties to
`0px` on what follows the row.

The shell's panel, sheet or side, has one surface, solid or glass, and a part it hosts paints no
fill of its own (decision 43). The panel sets `--kozmos-panel-part-fill` to `transparent` on its
content and its header. `BrowseCategoriesPanel` and `RoutePreviewPanel`, which fill their box with
the background colour when they stand alone, paint nothing there, so a glass panel shows through
them. On a solid panel they look as they did, since its fill is that same colour. `POIResultList`
and `POIDetailPanel`'s `sheet` presentation paint no fill anywhere, and neither, in the panel, does
the details card's summary strip, which was an opaque band across a glass sheet. Cards keep their
fill: each result, each route option, and a `panel` or `inline` details card.
A navigation `RouteSummary` whose product leaves `presentation` unset is hosted in the panel, in
its header as in its content: no card, padding, radius or shadow of its own. Outside the shell it
stays a standalone card.

On glass, text that is muted elsewhere takes the foreground colour, so it reads at 4.5:1 over any
map (decision 48); the glass itself is unchanged. The glass surface says so: `.kozmos-surface-glass`
sets `--kozmos-surface-muted-foreground` to the foreground colour, and the solid surface resets it.
A hosted part's muted text that sits on the panel reads the property: the route preview's "To"
and count of options, the details card's level line, hours, prices, notes, section headings and
gallery position in its `sheet` presentation, a gallery hosted on its own, and the empty states of
the browser, the route preview and the result list. Over a saturated map it read about 3.7:1 muted;
it now reads 9.7:1 or more. Muted text in a card of its own, a result, a route option or a `panel`
or `inline` details card, stays muted: it sits on the card, which says so. The same holds on every
glass surface, the floating cards' too (see Surface).

On iOS and Android the shell tells its panel's content how much space it already leaves
above it, so a part that brings its own top padding tops it up rather than adding to it
(GAP-083): `kozmosPanelInsetTop` and `kozmosPanelClearanceTop` in the SwiftUI environment,
`LocalKozmosPanelInsetTop` and `LocalKozmosPanelClearanceTop` in Compose. Under a grab
handle they are its 16-point row and 4 points of clearance, so the handle's target keeps
its WCAG 2.5.8 spacing. With no handle (a single detent), under a `panelHeader`, and in a
side panel, the shell supplies 16 points of inset and zero clearance. The header owns
its bottom gap, so the content scrolls below that fixed gap. `KozmosPOIDetailPanel`
in its sheet presentation, which paints no surface of its own, uses both, so its close
button sits as far from the panel's top as from its side: 16 and 16 under a handle, where
its header's buttons stay clear of the handle's circle, and 20 and 16 where they would not,
from its own width (decision 51; under 338 points or dp with favourite, save and close). The
panel and inline presentations
draw their own bordered card and keep their padding inside it: the space the panel leaves
lies outside that border. `KozmosBrowseCategoriesPanel` uses both for its first row too, in
the panel on both platforms: on iOS in either presentation, since the panel presentation
follows the panel's signal when hosted (standing alone it paints its own surface and keeps
its 16). `KozmosRoutePreviewPanel` uses both
for its destination row on both platforms. Under the grab handle the
`panelHeader` itself starts 4 points (4dp) below the handle's row, as the web's does. For a
part you place under a row of your own, set both values to zero: `.environment(\.kozmosPanelInsetTop, 0)`
and `.environment(\.kozmosPanelClearanceTop, 0)` in SwiftUI, and `0.dp` for both
CompositionLocals in Compose.

The shell also tells what it hosts which surface it sits on, `kozmosPanelSurface` in the
SwiftUI environment and `LocalKozmosPanelSurface` in Compose (solid or glass, nil outside a
shell), so a part paints no fill of its own there (decision 43). `KozmosRoutePreviewPanel`
paints none in the panel on both platforms; standing alone it keeps its background colour.
The category browser paints none in the panel on either platform, in both of its iOS
presentations, and keeps its fill standing alone, as the web's does. The details card's
sheet presentation paints none on either. On iOS the route preview's square fill also covered
the panel's rounded top corners; they show the map again.

The panel's surface also says when their muted text takes the foreground colour: on glass
(decision 48). On iOS every `kozmosSurface(_:style:)` tells what it holds which surface it is
(`kozmosSurfaceStyle` in the environment), the panel's included; in Compose the shell and the
cards with a `surface` provide `LocalKozmosSurfaceStyle`. The route preview's "To" and count of
options and the details card's muted lines read it; in the panel and inline presentations the
card says it is a surface of its own.

`usableRegions` accepts host-provided hinge-free rectangles in shell-local CSS pixels.
Auto mode can separate map and panel across those regions without remounting either.
This is a geometry input, not automatic foldable-device detection.

The `map` slot must be a real supported renderer; this component never draws substitute
map geometry. `onLayoutChange` reports shell-local renderer/panel bounds and occlusions.
Resolved padding is **map-local**, exposed through `onCollisionInsetsChange` and
`--kozmos-map-inset-*`. The SDK adapter applies it to the camera deliberately.

`safeAreaInsets` reserves edge space (including keyboard overlap supplied by the host);
do not subtract a keyboard again if it already resized the host. See
`docs/adaptive-map-layout.md` for the full coordinate and fallback contract.

## Registered attribution

Pass MapAttribution through the optional attribution slot, not through the renderer's map
slot. Registered corner controls keep equal 16-unit side/bottom insets, plus safe areas,
or the same gap above a bottom sheet. Attribution stays centered across the full map,
independent of a desktop search/POI panel. The larger measured corner is reserved equally
on both sides so unequal controls cannot shift the credits. In RTL the logical corners
mirror. If this centered slot has less than 128 units (room for the default brand), only attribution moves above the
corners. Tall side panels leave a clear footer band instead of covering the credits.
With too little room under an opened top bar, MapAttribution's brand gives way first, then the
corners, and the credits never clip (decision 58): the brand shows only when the whole
attribution fits, lifted above the corners when it sits there, and credits still too tall to
sit above the corners send the corners away and return to the bottom row. The brand comes back
once it fits again.
MapAttribution's transparent appearance aligns the credit text's bottom, rather than an
internally padded frame, with the corner frames at this inset.

The row contributes an attribution occlusion and bottom camera padding even when
bottomControlsPadCamera is false. Omitting the slot restores the prior layout. Long credits
stay on one horizontally scrollable line. Oversized custom branding is capped to at most
half the usable chrome band; it does not displace the entire panel. Capped sheets allow
content scrolling. Safe-area and host keyboard insets still apply.
The SDK adapter applies reported camera padding and owns provider content and deduplication.
Unregistered overlays and status messages still require host placement.

Native equivalents use `attribution: AnyView(...)` in SwiftUI and `attribution = { ... }` in
Compose. Native locale remains device/app-owned; there is no native language button.

## Browse and details in one panel

Wide side panels hug short content and scroll long content within their available
height. The assistant is the exception: `AICompanionPanel` fills the side panel's
height, so its input stays at the bottom and only its thread scrolls (GAP-124).
They reserve the bottom control row plus one 16-unit gap. Registered
bottom-start/end controls stay at the map's outer edges, not beside the panel;
placement mirrors in RTL. A corner popup uses the space below a short panel,
or the clear map beside a long panel when the lower band cannot hold a usable menu.
Bottom-sheet detents and separated/hinge layouts keep their existing sizing policy.

SwiftUI mirrors this through `KozmosPanelScrollView`, which fits its content when
hosted in a side panel. Compose content must retain bounded scrolling (for example,
a lazy list/grid) and must not force an infinite minimum height. Custom content
that explicitly fills available height can still take the panel's height cap.
On wide hosts the shell supplies a search header's 16-unit top inset; the header supplies
its own 16-unit horizontal padding. Compact headers keep the existing grab-handle clearance.

Use BrowseCategoriesPanel's search slot for SearchBar, not the shell's topBar. Dock the
panel at start on desktop; the same content becomes a bottom sheet on compact hosts.
Replace that panel content with POIDetailPanel when selecting a POI, keeping query and
category state in the host so closing details restores them. The interactive
Examples / Map browse flow stories demonstrate this composition, including focus transfer.
Those examples use illustrative data, not a live SDK. Native hosts own the equivalent
state transition using KozmosBrowseCategoriesPanel and KozmosPOIDetailPanel.
